Формат новой записи:

## D-001: Одна ветка и один PR

- Status: Accepted
- Date: 2026-10-26
- Почему: ревьюер читает порядок коммитов на PR сдачи, а не набор влитых feature-веток

Вся работа в ветке `clean-code` от `main` форка [Bogagree/clean-code-todo](https://github.com/Bogagree/clean-code-todo).

PR открываем в `main` своего форка и не мержим. `main` не коммитим. Файл `.github/workflows/check.yml` не меняем.

Шаг плана — один коммит на этой ветке. Отдельный `feat/*` на каждый шаг не заводим: так история, которую оценивают, останется одной цепочкой.

Первый коммит — `docs:` с этим планом. Он вне шести механических коммитов из задания. В коммиты настройки, форматирования и автофикса docs не попадают.

## D-002: Инструменты собираем сами

- Status: Accepted
- Date: 2026-10-26
- Почему: задание требует рекомендованный набор и три явных правила, без чужого пресета

npm. Скрипт `lint` запускает `eslint app.js`, скрипт `format` — `prettier --write .`.

`eslint.config.js` (flat config, ESLint 10):

- `js.configs.recommended` из `@eslint/js`;
- `languageOptions.globals` = `globals.browser` для `app.js`;
- правила `no-var`, `prefer-const`, `no-console` на уровне `error`;
- последним блоком `eslint-config-prettier`, чтобы линтер не спорил с форматтером.

`package.json` содержит `"type": "module"`, чтобы flat config с `import` читался. На тег `<script src="app.js">` это не влияет: в браузере файл остаётся обычным скриптом.

Пресеты Airbnb и Standard не подключаем. `eslint-plugin-prettier` не ставим.

`.prettierrc`: дефолты Prettier и `endOfLine: "lf"`. Рядом `.gitattributes` (`* text=auto eol=lf`) и `.editorconfig`.

`.prettierignore`: `node_modules`, `package-lock.json`, `.github`. `index.html` и `style.css` оттуда не исключаем.

`.gitignore` содержит `node_modules`.

Husky, `lint-staged` и скрипт `prepare` появляются только в своём коммите, после того как линтер уже молчит.

## D-003: Поведение и вид не меняем

- Status: Accepted
- Date: 2026-10-26
- Почему: чек-лист задания сверяет живое приложение, а не «как должно было быть задумано»

Контракт — [specs/clean-code.md](./specs/clean-code.md), раздел «Поведение». В том числе то, что легко принять за баг:

- строка из одних пробелов добавляется: проверка смотрит на пустую строку, без `trim`;
- в редактировании можно сохранить пустой текст;
- перенос между списками двигает тот же узел `li`, вместе с `editMode`;
- три стартовые задачи остаются в разметке.

`doctype` не добавляем: без него страница в quirks mode, смена режима может сдвинуть вёрстку.

## D-004: Синтаксис HTML и CSS чиним точечно

- Status: Accepted
- Date: 2026-10-26
- Почему: Prettier не разбирает два места, а правка «заодно» меняет то, что браузер уже нарисовал

`index.html`: элемент `p#topSectionForAddingElementToList` закрываем сразу после `label`. Вложенный `div` браузер и так выталкивает из `p`. Исходник приводим к уже построенному DOM.

`style.css`: правило `ul#completed-tasks label` не разбирается из-за пропущенной точки с запятой, поэтому зачёркивание и серый цвет сейчас не применяются. Правило удаляем. Точку с запятой не ставим: иначе выполненная задача станет зачёркнутой, и пункт «вид не изменился» пропадёт.

Остальное в этих файлах — коммит форматирования, не коммит синтаксиса.

## D-005: Имена классов, id и видимый текст не переименовываем

- Status: Accepted
- Date: 2026-10-26
- Почему: баллы за имена стоят на переменных и функциях в `app.js`, а визуальная проверка смотрит страницу

Класс `editMode`, id `new-task`, `incompleteTasks`, `completed-tasks`, классы вроде `aaa` и `more_inf`, подписи Edit / Save / Add, путь `./remove.svg` остаются. Семантические `header` / `main` не внедряем.

Переименования — только привязки в `app.js`, таблица в спеке.

## D-006: Что объединяем в логике, а что оставляем

- Status: Accepted
- Date: 2026-10-26
- Почему: общее знание выносим, а разный следующий шаг чекбокса не склеиваем

`taskCompleted` и `taskIncomplete` оба переносят тот же `li` и заново вешают события. Это одно знание — функция `moveTask`. Две тонкие функции направления остаются: у завершённой и незавершённой задачи следующий обработчик чекбокса разный.

Два цикла по стартовым спискам не сливаются в один цикл с таблицей пар. Общее там уже сделано `bindTaskEvents`. Циклы живут в одной функции `bindStarterTasks`, чтобы у файла была явная точка входа.

`createNewTaskElement` остаётся одной функцией. Она собирает одну строку в том порядке узлов, на котором держится flex. Дробить её на фабрики кнопок не из чего: у частей нет отдельной причины меняться.

## D-008: Фраза «следующий шаг» запускает один коммит

- Status: Accepted
- Date: 2026-10-26
- Почему: название коммита уже лежит в плане, повторять ветку и PR в каждом чате не нужно

Фразы «следующий шаг», «следующий пункт» и «next step» в этом репозитории — просьба выполнить ровно один шаг и опубликовать его.

1. Открыть [implementation-plan.md](./implementation-plan.md), взять блок **Next** и карточку этого коммита в [specs/clean-code.md](./specs/clean-code.md). Свериться с решениями, на которые карточка ссылается.
2. Сделать только этот шаг. Сообщение коммита — строка из дерева, дословно.
3. Закоммитить и запушить в `clean-code`. Новый PR не открывать: обновляется уже открытый. Не мержить.
4. Метки `[done]` и **Next** не сдвигать. Их обновляет последний шаг `docs: record lint counts, checklist, and deploy`.

Если открытых пунктов нет, остановиться и написать, что шагов не осталось. Скилл с тем же контрактом: `.cursor/skills/clean-code-next-step/SKILL.md`.
